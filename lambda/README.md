# Lambda processor

This directory contains the Python Lambda function responsible for processing events consumed from the `access-events` SQS queue.

The function is intentionally small: transport and retry behaviour are handled by SQS and the Lambda event source mapping, while the processor focuses on persistence and idempotency.

## Processing flow

```text
SQS access-events
       │
       ▼
 Lambda processor
       │
       ├────────► DynamoDB
       │          structured event
       │
       └────────► S3
                  raw payload
```

The Lambda is invoked asynchronously through an SQS event source mapping created by Terraform.

For each SQS message, the processor reads the original JSON payload and uses `event_id` as the stable identity of the event.

## Persistence

### DynamoDB

Structured event data is stored in:

```text
access-events
```

The table uses:

```text
event_id
```

as its partition key.

The processor uses a conditional DynamoDB write so an event that has already been persisted cannot create a second record with the same `event_id`.

### S3

The raw payload is stored in:

```text
s3://access-events-raw/events/YYYY/MM/DD/<event_id>.json
```

The object key is deterministic for a given event and date, so processing the same logical event does not create additional S3 object keys.

## Idempotency

SQS uses at-least-once delivery semantics, so a message may be delivered more than once.

The processor therefore treats `event_id` as the event identity.

A duplicate event is detected through the conditional DynamoDB write and is handled without creating an additional DynamoDB record.

The S3 destination also uses a deterministic key based on the event ID.

The root automated test explicitly verifies this behaviour by sending the same authenticated event twice and checking that the final state contains:

```text
DynamoDB records: 1
S3 objects:       1
```

Run the complete test with:

```bash
make test
```

from the repository root.

## Configuration

The function receives its runtime configuration through environment variables provisioned by Terraform:

```text
DYNAMODB_TABLE
S3_BUCKET
AWS_REGION
AWS_ENDPOINT_URL
```

`AWS_ENDPOINT_URL` points the AWS SDK used inside the Lambda container to the Floci endpoint reachable from the Docker network.

No resource names or credentials need to be supplied manually to the function at runtime.

## Dependencies

Python dependencies are declared in:

```text
src/requirements.txt
```

The package currently includes `boto3` explicitly rather than depending on a preinstalled Lambda runtime copy.

This makes the deployment artifact self-contained and satisfies the challenge requirement to package dependencies in the Lambda ZIP without using Lambda Layers.

## Building

The Lambda package is built with:

```bash
make build
```

from this directory.

The build:

1. removes any previous build output;
2. creates a temporary package directory;
3. installs the dependencies from `src/requirements.txt`;
4. copies the Lambda handler into the package root;
5. creates the deployment ZIP.

The resulting artifact is:

```text
build/lambda.zip
```

The handler is placed at the root of the ZIP so the configured Lambda handler can load it directly.

The complete challenge deployment builds this artifact automatically:

```bash
make deploy
```

from the repository root.

## Cleaning the build

Generated Lambda artifacts can be removed with:

```bash
make clean
```

The `build/` directory is generated and is intentionally not versioned.

## IAM permissions

The Lambda execution role is created by Terraform.

Its application permissions are restricted to the operations required by the processor:

```text
sqs:ReceiveMessage
sqs:DeleteMessage
sqs:GetQueueAttributes
dynamodb:PutItem
s3:PutObject
```

The permissions are scoped to the specific event queue, DynamoDB table and S3 bucket objects.

## Failure handling

If processing raises an error, the SQS/Lambda integration can redeliver the message.

The main queue is configured with a Dead Letter Queue and:

```text
maxReceiveCount = 3
```

so repeatedly failing messages can eventually be moved to `access-events-dlq` instead of remaining in the main queue indefinitely.

## Logs

Lambda execution logs can be retrieved using:

```bash
scripts/lambda-logs.sh
```

from the repository root.

They are also collected automatically by:

```bash
make evidence
```

and written under:

```text
logs/
```

The logs provide processing evidence that can be correlated with the `event_id` generated by `make test`.

## Local execution scope

The Lambda runs inside a Docker container managed by Floci.

The implementation targets the local challenge environment and uses Floci's AWS-compatible endpoints for DynamoDB, S3 and SQS integration.

No AWS account is required.
